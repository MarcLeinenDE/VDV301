## High-level fresh-read conclusions

The fresh read strongly supports the existing resolver architecture:

- service identity includes service name and IBIS-IP version;
- multiple versions of one service may coexist in one IBIS-IP system when they are technically separately addressable;
- clients select a compatible/preferred service version;
- different versions may use different ports/paths;
- SystemManagementService is a special case and may exist only once for one IBIS-IP version in an IBIS-IP system;
- HTTP POST is specified when request data is transferred, HTTP GET when no request data is transferred;
- DNS-SD carries technical service discovery;
- XML/XSD is the executable structure language for the specified service interfaces;
- Get/Subscribe/Unsubscribe and Retrieve semantics are explicitly distinguished.

These statements reinforce the superbranch/SDK invariant that mixed service versions must be routed exactly and that `latest wins` is invalid.

## New/refined Deep-Read findings

### DR3012-001 — wrong RFC number for IPv4 link-local/ZeroConf addressing

Classification: `external_standard_reference_error_candidate`
Confidence: high.

VDV 301-2 V1.0 §2.1.1 associates automatic ZeroConf addressing in the 169.254.x.x range with `RFC 2927`. The publication's own reference list identifies RFC 2927 as `MIME Directory Profile for LDAP Schema`.

External standards cross-check:

- RFC 2927 concerns an LDAP-schema MIME directory profile.
- RFC 3927 defines dynamic IPv4 link-local addressing in `169.254/16`.

The VDV reference number is therefore inconsistent with the described mechanism and is very likely a 2927/3927 citation error.

This is documentation/standards-reference audit knowledge. Do not silently rewrite the VDV rule in validation output.

### DR3012-002 — DNS SRV Weight selection semantics contradict RFC 2782

Classification: `external_standard_semantics_error_candidate`
Confidence: high.

The VDV DNS-SD/SRV explanation correctly states that lower `Priority` is preferred, but then describes the `Weight` field as if a lower weight were preferred for equal priority.

RFC 2782 instead defines Weight as relative selection weight for equal-priority records, with larger weights receiving proportionately higher selection probability.

This affects explanatory/runtime semantics, not XSD validation.

### DR3012-003 — SystemDocumentation `HertbeatIntervall` PDF/XSD type mismatch

Classification: `pdf_xsd_type_mismatch_candidate`
Confidence: high from native PDF table + exact official V1.0 XSD.

PDF `SystemDocumentationService.SystemConfigurationData` documents:

`HertbeatIntervall 0:1 IBIS-IP.duration`

Exact historical `IBIS-IP_SystemDocumentationService_v1.0.xsd` declares the corresponding member in `SystemDocumentationService.SystemConfigurationDataStructure` as:

`HertbeatIntervall` → `IBIS-IP.double`.

In the same XSD, `SystemDocumentationService.StoreSystemConfigurationRequestStructure/HertbeatIntervall` is `IBIS-IP.duration`, which matches the PDF's StoreSystemConfigurationRequest table.

Therefore the discrepancy is structure-specific, not a global spelling/type interpretation issue.

The misspelling `HertbeatIntervall` appears in both PDF and XSD and is part of the historical executable schema vocabulary; it must not be silently normalized to `HeartbeatInterval` during validation.

No prior first-pass finding for this exact mismatch was found in the audit files searched during this pass.

### DR3012-004 — DeviceState cross-reference points to DeviceClass section

Classification: `pdf_cross_reference_error_candidate`
Confidence: high from native text; visual table confirmation pending.

The intended cross-reference is therefore very likely §9.4.

### DR3012-005 — SystemManagement subscription headings use `SystemStatus` while operation table uses `ServiceStatus`

Classification: `pdf_label_or_heading_error_candidate`
Confidence: high.

The SystemManagementService operation table specifies:

- `SubscribeServiceStatus`
- `UnsubscribeServiceStatus`.

The subsequent section heading/prose instead uses:

- `SubscribeSystemStatus`
- `UnsubscribeSystemStatus`.

The Get operation and response data are also consistently named `GetServiceStatus`. This supports treating the `SystemStatus` headings as documentation terminology errors, not new executable operations.

### DR3012-006 — TimeService cross-reference `VDV 301-2-11`

Classification: `historical_cross_reference_candidate`
Confidence: unresolved until TimeService chronology/deep read.

§2.5 says SNTP implementation details are in `VDV 301-2-11`. In the current public numbering TimeService is 301-2-10 and 301-2-11 is VideoLiveService.

Do not classify this as a typo yet: the 2016 document may reflect an earlier/planned numbering sequence. Re-evaluate during the fresh TimeService deep read and historical publication check.

### DR3012-007 — StopService request description says "service to be started"

Classification: `minor_pdf_copy_paste_candidate`
Confidence: high from native text; semantic impact low.

The StopService request correctly describes stopping a service, but the `ServiceSpecification` field description says it refers to the service "zu startenden Dienst". The operation/table itself is unambiguously StopService.

No executable XSD change follows.
